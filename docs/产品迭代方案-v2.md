# 对公资讯聚合系统 — 需求与项目方案迭代 v2

> 编制日期：2026-08-12
> 基于：全量代码审查 + 真实数据源核验 + 银行对公业务场景重检
> 性质：产品判断与方案，非已实现功能

---

## 一、决策摘要

**核心判断：当前系统的问题不是功能不够多，而是"原料"和"管道"都没通。**

1. **数据源是第一瓶颈**：系统配置了 3 个采集源，但选择器和 URL 均为未经验证的占位代码（北京公共资源交易平台域名已失效），Celery 采集任务是空壳，爬虫入库后不触发 AI 处理。线上只有 5 条示例数据。**没有真实数据流入，AI 分类、线索挖掘、每日简报都是空中楼阁。**
2. **采集架构过度设计且断点过多**：Scrapy + Celery + Redis + 独立爬虫容器的架构，在只有 3-5 个目标站点、日均更新量几十到几百条的场景下，引入了 4 个断点（Celery 空任务、爬虫不触发 AI、爬虫容器单跑即退、beat 未注册关键任务），维护成本高于业务价值。
3. **需求层面缺少"行政事业"业务纵深**：现有 5 个业务分类（存款/贷款/投行/资金/供应链）是通用对公框架，但系统主要使用者是行政事业条线，缺少财政资金、专项债、国库支付、事业单位采购、土地出让等该条线最关心的商机类型和对应的数据源。
4. **MVP 应重新定义为**：3-5 个高价值权威源真实跑通 → AI 分类摘要 → 每日推送到企微/飞书 → 一键转线索跟进。先让客户经理每天早上收到一条有用的简报，再谈地图、热力图、SSO。

## 二、需求重检

### 2.1 目标用户与核心场景（重新校准）

| 角色 | 真实场景 | 核心诉求 |
|------|---------|---------|
| 对公客户经理（行政事业条线） | 每天早上到行里，想知道辖区内昨天有哪些政府采购/工程招标/政策发布可能带来存款或贷款机会 | 5 分钟内看完当日重点，直接判断哪些值得跟进 |
| 客户经理（公司条线） | 关注重点企业的工商变更、融资动态、中标信息 | 按企业/行业订阅，有动态及时提醒 |
| 团队长/部室管理者 | 掌握团队线索跟进情况，分配公海线索 | 看漏斗、督办、分配 |
| 支行领导 | 了解区域商机总量和转化情况 | 看汇总数据（非当前重点） |

**关键洞察**：客户经理的核心动作是"看资讯 → 判断价值 → 转线索 → 跟进"，而不是"在系统里浏览资讯"。系统的价值在于**主动推送精准商机**，而非被动等待用户打开 H5。当前系统把重点放在了 H5 浏览体验上，却没有打通推送链路，这是方向性偏差。

### 2.4 数据源获取策略：Build vs Buy

| 方案 | 内容 | 优点 | 缺点 | 建议 |
|------|------|------|------|------|
| A. 全自建爬虫 | Scrapy 维护所有源 | 免费、可控 | 政府站改版频繁、维护成本高、反爬 | P0/P1 源采用 |
| B. 付费 API | 企查查/天眼查 | 稳定、结构化 | 按次收费、不覆盖招投标公告 | P2 企业信息增强 |
| C. 商业聚合平台 | 千里马/启信慧眼 | 数据全、有商机标签 | 年费高（数万至十万级）、数据黑盒 | 暂不采用，自建跑通后对比 ROI |

**推荐 A + B 组合**：招投标和政策源自建（这些是公开信息，无版权风险），企业工商信息用 API 补全。

### 3.2 MVP 重新定义

**MVP 目标**：让行政事业条线客户经理每天早上收到一条企微/飞书消息，里面有 3-5 条与辖区相关的政府采购/工程招标/政策商机，点击可查看详情并一键转线索。

**MVP 范围（最小闭环）**：

```
5个P0数据源 → 每日定时采集 → AI分类摘要评分 → 人工审核（可选）
     → 每日简报生成 → 企微/飞书机器人推送 → H5查看详情 → 一键转线索
```

**MVP 不包含**：地图、搜索、企业 API 增强、SSO、数据看板、多支行。

**MVP 成功标准**（初始参数，上线后校准）：
- 每日新增真实资讯 ≥ 20 条（非示例数据）
- 简报推送到达率 100%
- 客户经理周活跃率 ≥ 50%（至少 3 天打开简报）
- 每周通过系统转化线索 ≥ 5 条

### 3.3 核心用户流程（MVP）

```
06:00  Celery beat 触发采集任务
       → 遍历 active 的 CrawlSource
       → RSS 源直接解析 feed；HTML 源用配置化选择器抓取
       → 去重（URL + 内容 MD5）
       → 新资讯入库，状态 pending_review

06:30  AI 处理任务（采集完成后自动触发）
       → 每条新资讯调用 AI：分类、摘要、业务启示、商机评分、提取企业名
       → 评分 ≥ 阈值自动 published；< 阈值进待审核

07:00  简报生成任务
       → 聚合昨日 published 资讯
       → 按业务分类分组
       → 生成简报文本（含标题、摘要、评分、链接）

07:30  推送任务
       → 调用企微/飞书 Webhook 发送简报到指定群
       → 高价值商机（评分 ≥ 80）单独即时推送（不等简报）

08:00  客户经理在企微/飞书群看到简报
       → 点击链接打开 H5 资讯详情
       → 判断有价值 → 点击"转线索" → 填写跟进备注 → 提交
       → 线索进入个人池，30天保护期

全天   客户经理可随时打开 H5 浏览/筛选/搜索资讯
       团队长可查看公海池、分配线索、督办跟进
```

## 四、项目方案迭代

### 4.1 采集架构调整

**现状问题**：
- 爬虫容器独立运行，只跑一个 spider 就退出，靠 restart 重启循环
- Celery `crawl_source_task` 是空壳
- 爬虫 pipeline 用 psycopg2 裸 SQL，与 ORM 双轨
- 爬虫入库后 AI 触发被注释

**调整方案**：

```
调整前（7个容器，4个断点）：
  celery-beat → crawl_source_task（空壳）✗
  crawler容器 → scrapy crawl gov_chaoyang（单跑即退）✗
  pipeline → 裸SQL入库 → AI触发被注释 ✗
  独立 nginx 目录（空）✗

调整后（5个容器，链路打通）：
  celery-beat → crawl_source_task（遍历CrawlSource，CrawlerRunner进程内执行）
                    → RssSpider / ConfigurableSpider（从DB读selector_config）
                    → SQLAlchemy pipeline（统一ORM）
                    → 入库后 process_news_task.delay()
  celery-worker → AI处理 / 简报生成 / 推送
  backend → FastAPI + 静态资源
  postgres + redis
```

**关键改动**：
1. 废弃独立 crawler 容器，爬虫代码移入后端，Celery worker 内通过 `CrawlerRunner` 执行；
2. 新增 `RssSpider`（feedparser 解析，10 行代码，最稳定）；
3. `ConfigurableSpider` 从 `CrawlSource.selector_config` 读取选择器，不再硬编码；
4. Pipeline 改用 SQLAlchemy session，与后端模型统一；
5. 入库后显式调用 `process_news_task.delay(news_id)`；
6. 删除根目录多阶段 Dockerfile 和空的 nginx/ 目录，统一用 docker-compose 分离部署。

### 4.2 安全与技术债（P0 必须修复）

| 项 | 问题 | 修复 |
|----|------|------|
| 认证后门 | admin/admin123 硬编码，非 admin 无法登录 | 统一走 password_hash 校验 |
| 密码哈希 | SHA256 | bcrypt（passlib） |
| JWT 密钥 | 默认弱密钥 | 生产强制环境变量，启动校验 |
| CORS | `*` + credentials | 收敛为具体域名白名单 |
| 越权 | viewer 可改资讯、任意用户可操作他人线索 | 接口加角色/归属校验 |
| 爬虫 DB URL | `postgresql+psycopg2://` psycopg2 不识别 | 爬虫侧剥离 `+psycopg2` |
| 定时任务 | 保护期回收/简报推送未注册 beat | 补注册，间隔改 crontab |
| Schema 双轨 | init.sql UUID vs ORM String(36) | 统一为 ORM 定义，init.sql 由 ALEMBIC 生成或统一 VARCHAR(36) |

### 4.3 部署方案

**现状**：Render 免费部署只有 backend + frontend + redis，无 worker/beat，线上无真实数据流。

**建议**：

| 环境 | 方案 | 说明 |
|------|------|------|
| 开发/演示 | Render 免费 + 手动触发采集 | 加一个手动"立即采集"按钮，worker 用 Render Background Worker（$7/月）或先用 FastAPI 后台任务凑合 |
| 行内试用 | 行内 Docker 主机 / 云服务器 | docker-compose 一键部署，5 个容器，2C4G 足够 |
| 生产推广 | 行内云 + 企微/飞书 SSO | 对接行内统一认证，PostgreSQL 用行内数据库 |

**Render 免费方案的妥协**：如果坚持免费，可将采集改为 FastAPI 启动时用 APScheduler 做进程内调度（不用 Celery worker），但简报推送和 AI 处理会占用 web 请求线程，仅适合演示。**正式使用建议至少 1 个 2C4G 云主机（约 100-200 元/月）跑 docker-compose。**

### 4.4 AI Prompt 调整方向

当前 AI Prompt 是通用分类，需针对银行对公场景调优：

- **分类**：扩展业务分类，增加"财政资金/专项债/事业单位采购/工程建设/土地出让/政策监管/企业动态/融资事件"
- **商机评分维度**（0-100）：
  - 资金规模（公告含金额：+30）
  - 主体明确度（可识别具体企业/单位：+25）
  - 辖区相关性（朝阳/北京：+20）
  - 时效性（本周内：+15）
  - 业务匹配度（与我行重点业务方向：+10）
- **业务启示**：从"这条资讯说明什么"改为"对我行业务的具体机会点和建议动作"，如"该项目预算 5000 万，建议营销项目资金监管账户和履约保函"
- **企业提取**：从正文提取中标单位/采购单位/建设单位名称，用于转线索
